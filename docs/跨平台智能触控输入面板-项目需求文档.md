## 1. 项目概述

### 1.1 项目名称

跨平台智能触控输入面板 —— Smart Touch Panel（简称 STP）

### 1.2 项目愿景

打造一款**轻量级、高定制、跨平台**的虚拟输入面板系统，让任何平板设备（iPad/Android平板）无需安装任何 App，通过浏览器即可变身为用户专属的输入控制台。

### 1.3 核心差异化优势

| 维度 | 现有方案 (Touch Portal / Deckboard) | 本题方案 |
|------|--------------------------------------|----------|
| 平板端安装 | ❌ 必须安装原生 App | ✅ 浏览器零安装，开网页即用 |
| iOS 支持 | ❌ Deckboard 不支持 iOS | ✅ 浏览器即可访问 |
| 跨设备同步 | 需登录账号 | ✅ Profile 文件即传即用 |
| PC 端编辑 | 独立编辑器 | ✅ 浏览器即编辑器，PC/平板均可编辑 |

## 2. 市场与竞品分析

### 2.1 竞品格局

| 产品 | 类型 | 平板端 | PC端 | 核心方案 | 费用 | 星标/用户量 |
|------|------|--------|------|----------|------|-------------|
| **Touch Portal** | 商业 | 原生 App (iOS/Android) | Windows/macOS 服务 | 本地 WebSocket + 输入模拟 | Free (8键/页) / Pro ~€15 | 主流竞品 |
| **Deckboard** | 开源 | 原生 App (Android 仅) | Windows/Linux (Electron) | Electron + WebSocket + 扩展 | Free / Pro 版 | GitHub 640★ |
| **Elgato Stream Deck** | 商业硬件+软件 | — | Windows/macOS | USB硬件 / 虚拟桌面版 | $149起 | 行业标准 |
| **STP 本题方案** | 开源 | **浏览器 (零安装)** | 轻量绿色服务 | 纯 Web + WebSocket | 开源免费 | — |

### 2.2 竞品关键技术特征

**Touch Portal**
- 最成熟的商业方案，功能完整
- 支持 OBS、Twitch、Spotify 等多种第三方集成
- 架构：原生 App + 桌面服务，WebSocket 通信
- 弱点：需要安装 App，免费版功能受限

**Deckboard** (rivafarabi/deckboard)
- GitHub 640★，Electron 技术栈
- 支持 Wi-Fi 和 USB (Android) 连接
- 支持键盘宏、打开网站/文件夹、多媒体控制、OBS 集成
- 最近更新：v3.2.0 (2026年6月)
- 弱点：Android 仅，需要原生 App

### 2.3 市场缺口

现有方案均依赖**原生移动端 App**，存在以下未满足的需求：
1. **零安装诉求**：用户不想在平板上额外装 App，尤其是临时使用场景
2. **iOS/iPadOS 覆盖**：Deckboard 不支持，Touch Portal 需安装
3. **纯 Web 方案自由度**：可自行部署、定制，不受应用商店审核限制
4. **自动窗口切换**：Touch Portal 和 Deckboard 均未实现此功能——当 PC 切换前台窗口时自动切换到对应键盘布局

## 3. 核心价值主张

### 3.1 即插即用

**核心原则：客户端零安装，Host 端正常安装。**

- 客户端（平板/手机）：无需安装任何 App，打开浏览器访问网址即可使用。这是本项目的核心差异化优势。
- Host 端（PC/Mac）：提供完整的安装程序（Windows 安装包 / macOS DMG），可正常写入系统、注册服务、开机自启等。
- 一句话定义：**"绿的"仅限客户端，Host 端不要求"绿色"——能用好功能比"免安装"更重要。**

### 3.2 形态自由

不局限于标准键盘，允许用户为任何特定任务（游戏、设计、开发、直播等）创建并保存完全自定义的按键布局。按键的位置、大小、颜色、图标、功能均可自由定义。

### 3.3 跨设备习惯同步

用户的个性化布局配置（Profile）可以跨设备迁移——以 JSON 文件形式导出/导入，实现"配置跟着人走"。

### 3.4 智能上下文感知

PC 端服务能识别当前激活的软件（如 Photoshop.exe），并**自动切换**到对应的键盘布局，实现零操作切换。

## 6. 交互与体验需求

### 6.1 连接方式

主连接方式为 Wi-Fi（全平台），Android 额外支持 USB 直连。

| 方式 | 平台 | 类型 | 延迟预期 | 适用场景 |
|------|------|------|----------|----------|
| **Wi-Fi 局域网** | 全平台 | 无线 | ~2-5ms（方向目标 <10ms） | 日常使用，统一主方案 |
| **USB 网络共享** | Android 平板 | 有线 | <10ms（硬指标） | 对延迟极度敏感的场景（如游戏） |
| **USB 网络共享** | iPad | ❌ 不支持 | — | iPad 无 USB tethering 功能 |

### 6.2 Profile 管理系统

- 创建、编辑、重命名、删除 Profile
- 复制现有 Profile
- 导入/导出为 JSON 文件
- 自动备份最近版本

### 6.3 双端交互设计

| 端 | 交互设备 | 设计特点 |
|----|----------|----------|
| **PC 端** (编辑器) | 鼠标 + 键盘 | 精确点击、右键菜单、拖拽、框选、快捷键、属性面板、网格对齐 |
| **平板端** (控制台) | 触摸 | 大控件尺寸、长按编辑、手势切换、视觉反馈 |

### 6.4 后台运行

- PC 端服务支持系统托盘化运行
- 可配置开机自启
- 关闭窗口不退出服务（仅隐藏到托盘）
- 明确退出操作（右键菜单 → 退出）

## 8. 关键技术实现方案

### 8.1 输入模拟引擎

| 平台 | 技术方案 | 关键 API |
|------|----------|----------|
| **Windows** | `SendInput` (user32.dll) | `pynput` / `ctypes` 封装 `SendInput` + `KEYBDINPUT` |
| **macOS** | `CGEvent` (CoreGraphics) | `pyobjc-framework-Quartz` → `CGEventCreateKeyboardEvent` |
| **Linux** | `uinput` / `XTest` | `python-evdev` / `pynput.linux` |

> **注意**：macOS 从 Catalina 起，输入模拟需要**辅助功能权限**（System Settings → Privacy → Accessibility）。首次运行需引导用户授权。

### 8.2 前台窗口监控

| 平台 | 技术方案 | 说明 |
|------|----------|------|
| **Windows** | `SetWinEventHook` + `GetWindowText` | 监听 EVENT_SYSTEM_FOREGROUND，获取窗口标题和 exe 名 |
| **macOS** | `NSWorkspace.sharedWorkspace().notificationCenter` | 监听 NSWorkspaceDidActivateApplicationNotification |
| **Linux** | `_NET_ACTIVE_WINDOW` (X11) / `wlr-foreign-toplevel` (Wayland) | — |

### 8.3 Host 端打包与分发

- **Windows**：使用 **Inno Setup** 或 **NSIS** 制作安装包
  - 安装 = 复制文件到 Program Files + 可选注册为 Windows Service
  - 卸载 = 删除文件 + 移除服务
  - 可选：NSSM 包装 Python 服务进程
- **macOS**：使用 `.app` bundle + **DMG** 分发
  - `py2app` 或 Electron 打包
  - 可选配置 LaunchAgent plist 实现用户级开机自启
- **系统托盘**：pystray 实现，右键菜单含"打开面板地址"、"打开编辑器"、"退出"
- **运行时**：建议使用 **Electron 外壳包装 Python 后端**，以获得原生系统托盘、更新机制和更好的用户体验

### 8.4 前端渲染优化

前端渲染策略按延迟层级区分：

| 场景 | 延迟目标 | 优化侧重点 |
|------|----------|-----------|
| Android USB 直连 | < 10ms（硬指标） | 全链路极致优化：轻量前端、事件直发、CSS transform |
| Wi-Fi（全平台） | < 10ms（方向） | 优化为主，接受合理波动 |

通用优化策略：

1. **避免重型框架**：React/Angular 的虚拟 DOM diff 在频繁触摸事件下有额外开销
2. **直接 DOM 操作**：按键按下/弹起的视觉反馈直接操作 DOM class，不经过状态管理
3. **触摸事件直达**：`touchstart` 事件不经过事件委托链，直接通过 WebSocket 发送
4. **CSS transform 动画**：按键反馈（按下缩放）用 CSS transform + will-change，不触发重排

### 8.5 前端框架推荐

| 方案 | 推荐度 | 理由 |
|------|--------|------|
| **Vanilla JS + 模板** | ★★★★★ | 极致性能、零依赖、单 HTML 文件即可 |
| **Preact** | ★★★★☆ | 轻量 (3KB)、接近 React 开发体验 |
| **SolidJS** | ★★★★☆ | 无虚拟 DOM，编译优化 |
| **React** | ★★★☆☆ | 生态丰富但渲染开销最大 |
| **Vue** | ★★★☆☆ | 性能尚可但重型 |

## 10. 触控交互设计规范

### 10.1 触摸目标尺寸规范

触摸目标（Touch Target）是屏幕上响应用户触摸输入的区域，可能大于按键的视觉尺寸。

| 规范来源 | 推荐尺寸 | 物理尺寸 | 说明 |
|----------|----------|----------|------|
| **Android** Material Design | **48dp** | ~9mm | 无障碍规范明确要求，目标间距 ≥8dp |
| **iOS** Human Interface Guidelines | **44pt** | ~6.5-7mm | Apple HIG 要求 |
| **Windows** Fluent Design | **40epx** | — | 微软建议触摸优化 UI 增至 44epx |

**本项目规范采纳**：采用 **Android 48dp 标准**（物理尺寸更大，约9mm，对触摸更友好）。

- 核心操作按键的触摸目标设为 **48px** 或更大
- 若视觉尺寸较小，触摸热区**必须扩展到推荐尺寸**
- 按键间保持 **≥8dp** 间距
- 使用相对单位（`vw`/`vh`/`rem`）适配不同屏幕

### 10.2 触觉/音频反馈规范

本项目**不依赖震动触觉反馈**。平板端触觉反馈存在严重的浏览器兼容限制——Web Vibration API 仅 Blink 内核支持，Firefox 已移除，Safari/WebKit 从未实现且正式反对。因此统一采用 **视觉反馈为主、音频反馈辅助** 的策略。

#### 各类操作反馈设计

| 操作类型 | 视觉反馈（全平台） | 音频反馈（可选） |
|----------|-------------------|-------------------|
| 按键点击 | 按下缩放 + 颜色变化 | 轻触音效 |
| 主按钮（保存/确认） | 明显颜色变化 + 阴影 | 确认音 |
| 长按编辑 | 过渡动画进入编辑模式 | 提示音 |
| 切换 Profile | 页面过渡动画 | 切换音效 |
| 滑动切换页面 | UI 跟随手指 | — |

#### 实现策略

- **统一使用视觉反馈** —— 所有平台都必须有点击态动画（缩放 + 颜色变化）
- **音频反馈可选增强** —— 使用 Web Audio API 生成轻触音效
- **按键按下** `transform: scale(0.92)` + 即时颜色变化
- **所有反馈在 50ms 内完成**，保证交互即时感

### 10.3 视觉反馈规范

| 交互阶段 | 反馈要求 | 实现方式 |
|----------|----------|----------|
| **按下 (Touch Down)** | 即时反馈，紧贴手指 | CSS :active / touchstart 事件加 class |
| **移动 (Drag/Move)** | UI 跟随手指 | `touchmove` 事件，直接设置 transform |
| **抬起 (Touch Up)** | 确认操作完成或取消 | 若滑出目标区域取消操作，视觉指示 |
| **长按操作** | 进入编辑模式 | 定时器 + 进度条环状动画 |

#### 设计要点

- 按键被点击时有**点击态**（`transform: scale(0.92)` + 颜色/阴影变化）
- 长按触发的编辑模式有**明确的视觉过渡动画**
- 操作成功/失败通过**视觉变化**（按键闪烁、颜色变化）给予反馈
- 关键操作使用 `will-change: transform` 优化渲染性能

### 10.4 通用交互设计原则（Apple HIG 五大原则）

1. **美学集成度**：界面外观与功能紧密融合，美观且实用
2. **一致性**：交互方式在整个应用中保持一致
3. **直接操控**：用户直接操控屏幕按键，操作结果直观可见
4. **反馈**：每次操作得到即时确认，长时间操作有进度更新
5. **用户控制**：可建议操作或警告风险，但不剥夺用户决定权（如删除确认框）

### 10.5 触控交互模式

| 手势 | 用途 | 说明 |
|------|------|------|
| **点击 (Tap)** | 激活按键、选择项目 | 基础交互 |
| **长按 (Long Press)** | 进入编辑模式、上下文菜单 | 平板端编辑按键位置/大小 |
| **拖拽 (Drag)** | 移动按键、调整布局 | UI 跟随手指 |
| **双指捏合 (Pinch)** | 缩放视图、调整按键大小 | 精细调整布局 |
| **滑动 (Swipe)** | 切换页面、切换 Profile | 左右滑动切换布局页 |

### 10.6 无障碍设计

1. 所有交互元素触摸目标 ≥ **48dp**
2. 每个按键有描述功能的**文本标签**（label 字段）
3. 按键文字与背景保持**高对比度**
4. 按键状态不依赖颜色变化，结合**图标或文字变化**
5. 支持键盘导航（PC 端编辑模式）

## 12. 连接与使用流程 (User Journey)

### 12.1 首次使用流程

```
步骤 1: 启动
  └─ PC 端双击运行服务软件
      ├─ 自动以后台服务方式运行
      ├─ 系统托盘显示图标
      └─ 自动生成访问信息

步骤 2: 连接
  └─ 打开平板浏览器
      ├─ 扫描 PC 端显示的二维码
      └─ 或输入 http://stp.local:8080

步骤 3: 使用
  └─ 平板加载默认键盘布局
      └─ 点击按键即可控制 PC

步骤 4: 自动切换
  └─ PC 切换前台窗口时
      ├─ 服务自动识别窗口
      └─ 通知平板切换到对应 Profile

步骤 5: 定制
  └─ PC 端: 打开浏览器 → 进入编辑器
  └─ 平板端: 长按按键 → 编辑模式微调
```

```
开机 → PC 端自动启动（服务后台运行）
     → 平板开机 → 打开浏览器 → 访问 stp.local
     → 自动连接 → 显示上次使用的布局
     → 开始操作 ...
     → 切换窗口 → 布局自动切换
     → 结束 → 关闭浏览器标签页即可
```

## 13. 非功能性需求

### 13.1 性能

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 输入延迟 (Android USB 直连) | < 10ms（硬指标） | USB 有线场景，端到端延迟硬上限 |
| 输入延迟 (Wi-Fi / 全平台) | < 10ms（方向） | Wi-Fi 场景作为优化方向，接受合理波动 |
| WebSocket 吞吐 | 持续 ≥ 100 msg/s | 支持高频连续按键 |
| 连接稳定性 | 0 断开/小时 | 局域网下长连接稳定 |
| 内存占用 (Host 端) | < 50MB | 空闲状态 |
| CPU 占用 (Host 端) | < 5% | 空闲状态 |

### 13.2 稳定性

- PC 端核心服务具备**进程守护**能力，异常退出后自动重启
- WebSocket 断线自动重连（指数退避策略）
- 服务异常时不影响已连接的系统（不造成键盘鼠标异常表现）

### 13.3 跨平台

| 平台 | 优先级 | 状态 |
|------|--------|------|
| **macOS** | P0 | 首发平台 |
| **Windows** | P1 | 首发后次之 |
| **Linux** | P2 | 远期支持 |

### 13.4 安全

- 仅限局域网连接，不暴露到公网
- 连接无需认证（局域网信任模型）
- 敏感操作（如键盘记录、宏执行）不做持久化

### 13.5 包体大小

- Host 端安装包（Windows）≤ 50MB（含 Python 运行时和依赖）
- 客户端零安装（仅浏览器加载 SPA，首次约 500KB）

## 14. 技术风险与应对策略

### 14.1 输入模拟权限（macOS）

| 风险 | macOS 需要辅助功能授权，Windows 无此问题 |
|------|------------------------------------------|
| **影响** | macOS 首次运行需要用户手动授权，否则输入模拟失败 |
| **策略** | (1) 首次运行弹出引导界面，指向系统设置 → 隐私 → 辅助功能
(2) 检测运行状态，授权未完成时给出明确提示
(3) 对应的 PyObjC 调用会静默失败，需在日志中输出诊断信息 |

### 14.2 浏览器渲染延迟

| 风险 | 浏览器渲染管线在复杂布局下可能引入额外延迟 |
|------|---------------------------------------------|
| **影响** | 高频操作场景（游戏）下延迟可能超出硬指标范围 |
| **策略** | (1) 轻量前端方案（Vanilla JS 或 Preact，避免 React/Vue）
(2) CSS `will-change` + `transform` 优化，不触发重排
(3) 按键事件直发 WebSocket 不走事件冒泡链
(4) Android USB 直连场景额外进行渲染调优以满足 <10ms 硬指标 |

### 14.3 iPad USB 有线连接不可用

| 风险 | iPad 不支持 USB 网络共享（USB tethering） |
|------|-------------------------------------------|
| **影响** | iPad 用户无法通过有线获得比 Wi-Fi 更低的延迟 |
| **策略** | (1) 主连接方案统一为 Wi-Fi，USB 仅作为 Android 可选增强
(2) 文档中明确标注限制 |
| **已确认** | ✅ 接受此限制，不追求 iPad 有线方案 |

### 14.4 iOS WebSocket 后台断开

| 风险 | iOS Safari 页面切到后台后 WebSocket 断开 |
|------|------------------------------------------|
| **影响** | 用户切到其他 App 后返回需要重连 |
| **策略** | (1) 自动重连机制（页面 `visibilitychange` 事件触发恢复）
(2) 重连后同步当前 Profile 和按键状态
(3) 过渡期间显示"重新连接中"友好提示 |
| **已确认** | ✅ 接受重连间隙的影响 |

### 14.5 WebKit 评估约束

| 风险 | iOS/iPadOS 所有浏览器强制使用 WebKit 内核 |
|------|------------------------------------------|
| **影响** | 依赖非标准 Web API 的功能在 iPad 上可能不可用 |
| **策略** | (1) 功能开发时评估 WebKit (Safari/iPad) 兼容性
(2) 使用标准 Web API，不依赖 Blink-only 特性
(3) 受限时在文档或界面中明确告知 |
| **已确认** | ✅ 此约束为评估条件，非阻止性问题 |
